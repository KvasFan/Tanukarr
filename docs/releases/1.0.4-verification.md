## Backup reproduction and implementation

Compared with accepted upstream base `57816c149d02f95543973fefb4780c4495f8121c`,
`BackupCommand`, both task controllers and the Tasks frontend were unchanged.
The task manager's completion logic was unchanged apart from unrelated fork
task registrations. Manual backups were explicitly excluded from scheduled-task
timestamp updates; the executor still publishes a completion event on failure.
This is inherited behavior, rather than an attributed fork regression.

The isolated published 1.0.3 image
`sha256:bdc828ac463e93924f62e7f0fe0ef036282ec46f7f51a6cb78f3d1e0e48028e3`
(source `d2afdbf8a963b8a70c43cd6863d2927c685bb9f5`) reproduced the bug.
A manual Backup command completed and produced a **27,499-byte ZIP** with
valid CRC, a valid SQLite database and `config.xml`; Last Execution, Last Start
Time and Next Execution remained unchanged. Its receipt correctly records
`passed: false`. A separate real Chromium Tasks-button check also reproduced
the stale display, with no page errors or outbound browser requests. Both
owned fixtures were fully removed. Neither accessed the owner's configuration.

The source change lets manual backups update the task, records only successful
backup completion, and persists timing before task-controller SignalR sync.
Manual/scheduled archive types remain distinct. Eleven database-backed test
cases cover successful manual/scheduled triggers, failed or incomplete commands,
cache/database consistency, schedule timing and restart persistence. Their
execution is included in the passing newly compiled focused test run below.

## Watched-state scope and safety

The design reads one selected Jellyfin user/library, validates complete pages,
and matches registered physical file paths. Missing/unmatched items do not erase
local watched history. Monitoring changes and list writes are separate opt-ins.
Migrations 248/249 persist local state and queued progress. The private source
authority is omitted from public episode resources.

AniList/MAL scalar progress uses a watched continuous native episode prefix and
verified own-account existing entries. Trakt/SIMKL use explicit episode history
with compatible native identities. Provider fixtures and actual local Jellyfin
playback-state changes establish different scopes; neither proves a live private
external account accepted a write. See [Jellyfin watched status](../jellyfin-watched.md).
