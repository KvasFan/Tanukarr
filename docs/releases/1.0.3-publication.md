## Late upstream recheck and dependency decision

The original [upstream audit](../upstream-audit-2026-10-13.md) retains its
21:09 UTC checkpoint. At 22:44:13 UTC, gaboy's main branch was
`f33ce343adf005ef3b29eef31710b597598d6c06`, eleven commits ahead of its earlier
main head. Six of the first eight were already adapted/credited; two remain the

and gaboy's inspected development branch, had not advanced.

Matt Flowers authored the three newly reviewed commits:

- [`39f919970c0ea9652055fcbf88603429d85082f0`](https://github.com/gaboy498-byte/Sonarr-Pro/commit/39f919970c0ea9652055fcbf88603429d85082f0): ImageSharp 4.1.3 and Windows reference cleanup.
- [`1312455c49fd9d7c3861b3b1674cbe44f6a1a799`](https://github.com/gaboy498-byte/Sonarr-Pro/commit/1312455c49fd9d7c3861b3b1674cbe44f6a1a799): source provenance and Windows validation documentation.
- [`f33ce343adf005ef3b29eef31710b597598d6c06`](https://github.com/gaboy498-byte/Sonarr-Pro/commit/f33ce343adf005ef3b29eef31710b597598d6c06): manual-only Docker publication.

Main/tag attempt 1 was intentionally cancelled at 22:48:24/22:48:21 UTC before
release for this audit; those cancellations were not product/test failures.
In an isolated worktree, changing only ImageSharp to 4.1.3 let the complete
Debug solution compile in 49.69 seconds with one missing-license warning and
zero errors. Release failed in 5.96 seconds, exit 1 and one error:
`No Six Labors license found` for `Sonarr.Core`. No applicable key was configured;
the [official documentation](https://docs.sixlabors.com/articles/imagesharp/index.html)
describes direct-reference build-time key enforcement.

No candidate tests, Docker build or cover-runtime verification were performed,
and no license enforcement was bypassed or private key reused. ImageSharp
remains 3.1.12 with its disclosed findings. A valid applicable key and independent
Release/Linux/cover checks are required before adoption; the fork's Windows
claims are not Tanukarr tests. Its reference removal targets 10.0.10; this project
uses 10.0.12 with a clean existing restore/build, so it is not transplanted.
Manual-only publication would remove the authorized gated main/tag workflow and
is not adopted. Provenance clarification is reflected in Tanukarr documentation
without borrowing the fork's tests or licensing validation. Both workflows were
rerun as attempt 2 on the unchanged release source.

## Deployment

The first published-image deployment failed its protected-database comparison:
`Config` and `Episodes` changed after startup. The helper retained the failure
receipt and rolled back to the verified 1.0.2 instance without restoring a stale
data snapshot.

The subsequent read-only audit found 33 complete table hashes unchanged and
intact row counts across all 35 tables. `Config` retained eight rows; only the
value of `prosearchhistory` changed. `Episodes` retained 5,074 rows; only
`LastSearchTime` changed in 440 rows. Episode identities, numbering, media
references and all other fields remained unchanged, as did the configuration
XML. Existing queued searches resumed on restart; the deployment did not submit
new searches.

The second attempt took a fresh consistent stopped-instance backup at
**23:39:22 UTC**. It preserved SQLite integrity, all 35 protected tables and row
counts, the configuration XML, 292 series, one configured list, 292 list items,
zero global exclusions and 5,074 episodes. At readiness, **23:39:29 UTC**, no
raw table hash had changed. The follow-up checkpoint at **23:39:47 UTC** recorded
changes only to `Config.prosearchhistory`'s value and `Episodes.LastSearchTime`;
all other fields and row counts remained unchanged. Raw hashes were retained,
and 24 protection-verifier checks passed with only those two activity fields
excluded from the stable-field comparison. This is not an unchanged-raw-hash
claim after resumed searches.

Five read-only checks on the deployed owner instance passed: both v3 and v5
reported six profiles and 22 quality definitions, with 22 numeric minimum and
preferred values, 16 numeric maxima and six Unlimited maxima; the codec endpoint
reported 15 entries. The first verifier incorrectly required null maxima to be
present, although the documented API omits them. Its failed receipt remains;
only verifier normalization changed before the successful retry. No validation
POST, owner import or media movement was performed. Private backup paths,
database values and credentials are excluded from this report.

## Security and limits

The completed published-image Trivy 0.75.0 all-severity scan found **zero
Critical, 21 High, 23 Medium and five Low occurrences**, totaling 49 across
15 distinct CVEs and 19 package/CVE pairs, with zero detected image secrets.
These counts match the amended-source local scan. The High findings
are three distinct ImageSharp 3.1.12 advisories, `CVE-2026-106110`,
`CVE-2026-106113` and `CVE-2026-106115`, repeated across seven dependency files.
The two ImageSharp Medium advisories and operating-system findings remain in
the full report; advertised 4.1.2 fixes are not included. Owner configuration
secrets are outside the image-scan scope.

Changed-source Semgrep used 27 C# rules across 15 production paths, complete
parsing and zero scanner errors. It retains one INFO authorization audit finding
on the inherited abstract REST controller, triaged against authenticated API
fallback policy/middleware rather than suppressed. The frontend audit reports
three High occurrences of the existing, unpatched
[`braces` advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
in Stylelint/PostCSS build dependencies. Node and `node_modules` are absent from
the runtime stage; the build-chain finding remains disclosed.

Controlled provider/RSS fixtures establish their exercised contracts, not
external uptime, private-account imports or real indexer downloads. No PostgreSQL
runtime, live private MAL or premium SIMKL execution is claimed. The separate
Jellyfin fixture does not establish an owner-server scan or general scan timing.
