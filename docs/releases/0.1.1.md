# Tanukarr 0.1.1

Tanukarr **0.1.1** is a maintenance release of 0.1.0. It keeps the inherited
database schema (253), the v3/v5 APIs, provider identities and every 0.1.0
feature: graphical account creation, collection and quality fixes, seven
configurable metadata catalogues, native films and IMDb lookup, list filtering,
download clients, imports, backups and Jellyfin refresh/watched state. Back up
the configuration before upgrading; use a compatible configuration backup when
restoring an older image.

## Changes

- Removing a pending release (delayed or waiting for a download client) through
  the v3 API works again. `DELETE /api/v3/queue/{id}` and the bulk endpoint
  resolve the per-episode v3 queue ids instead of answering `404 NotFound`, so
  third-party v3 clients can clear such items. Upstream Sonarr `develop` still
  carries the same mismatch at `2b39049ee`.
- A pending release removed from the queue, from the web interface (v5) or
  through v3, disappears immediately. Previously the database row was deleted
  but the in-memory pending list kept listing it until the next RSS sync, a
  series/profile edit or a restart. The list is now updated at once and the
  queue broadcasts the change.
- Six regression cases cover the v3/v5 lookups, id separation and immediate
  removal from both queue views.
- The integration-test client serializes request bodies with the application's
  Newtonsoft settings. RestSharp 106's bundled serializer turned the fork's
  non-empty movie-category default and the codec-multiplier dictionary into
  shapes the API rejects, which hid eight integration tests; no API behaviour
  changed.
- The Dockerfile builds the UI and backend stages on the build host's own
  architecture and cross-publishes the requested runtime identifier, so an
  arm64 image no longer requires emulated compilation. Published release images
  remain `linux/amd64`; any other architecture needs its own verified artifact
  before it can be called supported.

## Upgrade

Pull `ghcr.io/kvasexpert/tanukarr:0.1.1` and recreate the container. No
database migration beyond schema 253 runs; a 0.1.0 configuration starts
directly. After every start the pending-release list is rebuilt in the
background, so a queue holding thousands of pending releases can take a few
minutes before `queue/status` reports them. Docker `restart` alone keeps the
old image; use `docker compose pull` followed by `docker compose up -d`.

## Installation and verification

Use the [Docker installation guide](../docker-installation.md). The published
image is `ghcr.io/kvasexpert/tanukarr:0.1.1`; `latest` selects the tested
release. Configuration and media mounts remain compatible with 0.1.0.

The [verification ledger](0.1.1-verification.md) records the checks executed
for this release's source, including the
[October 17 local deployment ledger](../local-deployment-verification-2026-10-17.md)
that found and reproduced the queue defects. The hosted publication evidence
(exact digest, assets and runtime reports) belongs to the 0.1.1 publication
report once the release workflow has run. Historical 0.1.0 reports keep their
original identities and are not evidence for this build. This release must not
be described as vulnerability-free; the 0.1.0 security inventory remains the
latest public-image scan until a new one is recorded.
